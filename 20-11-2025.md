# README.md

## Docker Multi-Stage Build para Aplicación .NET 8.0

Este README documenta la implementación de un Dockerfile multi-stage para una aplicación .NET 8.0, incluyendo conceptos clave y mejores prácticas.

## 📁 Estructura del Dockerfile

### STAGE 1: Build (Compilación)

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /code
COPY Helloworkv2.csproj .
RUN dotnet restore
COPY . .
RUN dotnet build
```

**Propósito:** Compilar la aplicación usando el SDK completo de .NET

### STAGE 2: Runtime (Imagen Final)

```dockerfile
FROM mcr.microsoft.com/dotnet/runtime:8.0 AS runtime
WORKDIR /app
COPY --from=build /code/bin/Debug/net8.0/Helloworkv2 .
CMD ["/app/Helloworkv2"]
```

**Propósito:** Crear una imagen optimizada solo con el runtime necesario

## 🤔 Preguntas y Respuestas Importantes

### ¿Por qué pesa mucho la imagen?

- **Problema:** Usar SDK en producción incluye herramientas de desarrollo innecesarias
- **Solución:** Multi-stage build separa compilación (SDK) de ejecución (Runtime)

### ¿Cuál es la diferencia entre SDK y Runtime?

#### En .NET:

- **SDK:** Contiene todas las herramientas para desarrollar, compilar y ejecutar
- **Runtime:** Solo contiene lo necesario para ejecutar aplicaciones (.dll, .exe)

#### En Java (Comparación):

- **JDK:** Kit de desarrollo completo (como SDK de .NET)
- **JRE:** Java Runtime Environment (como Runtime de .NET)

### ¿Para qué sirve .dockerignore?

Sí, ayuda a excluir archivos innecesarios y reduce el tamaño del contexto de build.

## 🚀 CI/CD Pipeline Concepts

### CI (Integración Continua)

- **Propósito:** Detectar errores de código tempranamente
- **Limitación:** No detecta errores de lógica de negocio
- **Beneficio:** Automatiza pruebas y compilación

### CD (Despliegue Continuo)

- **Releases:** Gestión de versiones y despliegues
- **Deployment Groups:** Servidores destino para despliegue
- **Artifacts:** Artefactos generados (.dll, .exe, imágenes Docker)

## 🛠️ Mejores Prácticas

1. **Usar multi-stage builds** para optimizar tamaño de imagen
2. **Separar SDK de Runtime** en producción
3. **Implementar .dockerignore** para excluir archivos innecesarios
4. **Usar imágenes específicas** según el ambiente (desarrollo vs producción)

## 📝 Notas de Clase Importantes

### Conceptos Clave:

- En servidores de producción **NO** necesitamos herramientas de desarrollo
- Solo requerimos el **runtime** y los **artefactos compilados**
- Para Node.js con TypeScript también se requiere **transpilación**
- El SDK incluye compiladores, debuggers y otras herramientas de desarrollo

### Errores Comunes:

- ❌ Usar `FROM mcr.microsoft.com/dotnet/sdk:8.0` en producción
- ✅ Usar `FROM mcr.microsoft.com/dotnet/runtime:8.0` en producción
- ❌ No implementar multi-stage builds
- ✅ Separar etapas de build y runtime

### Optimización de Imágenes:

- **Multi-stage builds** reducen significativamente el tamaño
- **.dockerignore** evita copiar archivos innecesarios
- **Runtime images** son mucho más pequeñas que SDK images

## 📋 Pipeline de Azure DevOps

### Configuración Service Connection:

1. **Project Settings** → **Service connections**
2. **New service connection** → **Docker Registry**
3. **Docker Hub** configuration:
   - URL: `https://index.docker.io/v1/`
   - Docker ID: Username de Docker Hub
   - Password: Personal Access Token (no la contraseña de Google)

### YAML Pipeline Example:

```yaml
- task: Docker@2
  inputs:
    containerRegistry: "dockerhub-connection"
    repository: "username/image-name"
    command: "buildAndPush"
    Dockerfile: "**/Dockerfile"
```
