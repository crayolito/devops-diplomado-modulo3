# Infraestructura y Kubernetes - Apuntes de Clase

## Plan de Salvaje y Problemas de Infraestructura

### Problemática Inicial
- **Caída del sistema**: El sistema dejó de funcionar completamente
- **Pérdida de datos**: 300-400 pedidos no se registraron correctamente
- **Registro de preventas**: El sistema estuvo caído 3 horas, se tuvo que procesar todo manualmente

### Solución Propuesta: Kubernetes
Para evitar este tipo de problemas, se propone implementar **Kubernetes** como orquestador de contenedores.

#### Beneficios de Kubernetes:
- **Balanceo de carga**: Si TitoStore se pone a procesar algo pesado, Kubernetes haría un balanceo automático
- **Alta disponibilidad**: Crea múltiples instancias (réplicas) del sistema
- **Recuperación automática**: Si una instancia falla, hay respaldos disponibles
- **Escalabilidad automática**: Se pueden configurar 4 instancias como respaldo

### Escalabilidad y Costos
- **Escalado bajo demanda**: La escalabilidad es automática según la necesidad
- **Gestión de costos**: Solo se pagan los recursos que se utilizan
- **VPS adicionales**: Se pueden agregar más servidores virtuales si la aplicación lo requiere
- **App Services**: Utilizamos los servicios de aplicación disponibles

#### Monitoreo y Garantías
- **Monitoreo continuo**: Permite supervisar el estado de todas las instancias
- **Garantía de réplicas**: Kubernetes garantiza mantener 5 copias de cada instancia
- **Tranquilidad operativa**: "Podemos dormir tranquilos" - TitoStore tendrá monitoreo y alarmas
- **Herramienta poderosa**: Todo se puede configurar mediante código

## Despliegues Continuos

### Problemas Tradicionales
- La página no responde durante despliegues
- Cortes de servicio al desplegar en producción
- Tiempo fuera de servicio (downtime)

### Ventajas de Kubernetes para Despliegues
- **Sin cortes de servicio**: Los despliegues no afectan la disponibilidad
- **Portabilidad**: Funciona en Azure, AWS, Google Cloud
- **On-premise**: Se puede implementar en granjas de servidores propios
- **Flexibilidad**: Permite crear tu propio provider con red on-premise

## Arquitectura de Kubernetes

### ¿Qué es Kubernetes?
Un **orquestador de contenedores** que gestiona clusters de máquinas.

### Componentes del Cluster

#### Estructura Jerárquica
```
CLUSTER
├── NODO MASTER (Control Plane)
└── NODOS SECUNDARIOS
    └── PODS
        └── CONTENEDORES
```

#### Nodos
- **Conjunto de máquinas**: Pueden ser físicas o virtuales
- **Pods dentro de nodos**: Cada nodo contiene múltiples pods
- **Contenedores en pods**: Dentro de cada pod hay uno o más contenedores

### Nodo Master (Control Plane)

El nodo maestro administra todos los nodos secundarios y contiene:

#### 1. Control Manager
- **Función**: Verificar el estado actual del cluster
- **Responsabilidad**: Asegurar que el estado deseado coincida con el estado real

#### 2. Scheduler
- **Función**: Decidir en qué nodo se colocará cada pod
- **Proceso**: Analiza recursos disponibles y asigna pods óptimamente

#### 3. Kubelet
- **Definición**: Agente que controla y gestiona el trabajo
- **Función**: Mantener los contenedores ejecutándose correctamente

#### 4. K-proxy (Kube-proxy)
- **Función**: Comunicar los nodos entre sí
- **Red**: Gestiona las reglas de red y balanceo de carga

#### 5. API Server
- **Función**: Expone la API de Kubernetes
- **Comunicación**: Permite interactuar con Kubernetes mediante kubectl

#### 6. etcd
- **Definición**: Base de datos de Kubernetes
- **Contenido**: Almacena toda la configuración y estado del cluster

## Comandos Básicos de kubectl

### Comandos de Consulta
```bash
# Ver todos los nodos del cluster
kubectl get nodes

# Ver todos los pods
kubectl get pods

# Ver namespaces
kubectl get ns

# Ver pods del sistema Kubernetes
kubectl -n kube-system get pods

# Ver información detallada
kubectl get pods -o wide
```

```bash

# Aplicar configuración desde archivo
kubectl apply -f 01-pod.yml
```

## Configuraciones YAML

### Ejemplo 1: Pod con Múltiples Contenedores
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-monitor-pod
spec:
  containers:
  - name: nginx
    image: nginx:latest
    ports:
    - containerPort: 80
  - name: monitor
    image: busybox
    command: ["sh", "-c", "while true; do echo Monitor running; sleep 10; done"]
```

**Resultado**: Un pod con 2 contenedores (nginx + monitor)

### Ejemplo 2: Deployment con Réplicas
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-monitor
spec:
  replicas: 5
  selector:
    matchLabels:
      app: nginx-monitor
  template:
    metadata:
      labels:
        app: nginx-monitor
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        ports:
        - containerPort: 80
```

### ¿Por qué usar Deployments en lugar de Pods directos?

#### Ventajas de los Deployments:
1. **Réplicas automáticas**: Especifica cuántas copias quieres (en el ejemplo: 5)
2. **Auto-recuperación**: Si borras un pod, Kubernetes automáticamente levanta otro
3. **Gestión simplificada**: Es como una "plantilla" que especifica los contenedores
4. **Escalabilidad**: Fácil aumentar o disminuir el número de réplicas

#### Concepto de Réplicas:
- **5 réplicas = 5 pods idénticos** ejecutando nginx
- **Alta disponibilidad**: Si uno falla, los otros 4 siguen funcionando
- **Balanceo de carga**: Las peticiones se distribuyen entre los 5 pods

## Respuestas a Preguntas Técnicas

### Sobre Control Manager:

#### ¿Qué funciones específicas realiza el Control Manager?
El **Control Manager** es en realidad un conjunto de controladores que ejecutan diferentes tareas:

- **Node Controller**: Monitorea el estado de los nodos y detecta cuándo fallan
- **Replication Controller**: Asegura que el número correcto de pods esté ejecutándose
- **Endpoints Controller**: Gestiona los objetos de endpoints (servicios y pods)
- **Service Account Controller**: Crea cuentas de servicio predeterminadas para nuevos namespaces
- **Deployment Controller**: Gestiona las actualizaciones y rollbacks de deployments

#### ¿Cómo detecta cuando el estado actual no coincide con el deseado?
Mediante un **bucle de control continuo** que:
1. **Lee el estado deseado** desde etcd (la base de datos)
2. **Observa el estado actual** del cluster
3. **Compara ambos estados** constantemente
4. **Toma acciones correctivas** cuando hay diferencias
5. **Repite el proceso** cada pocos segundos

**Ejemplo práctico**: Si tienes 5 réplicas configuradas pero solo 3 están corriendo, el Control Manager detecta esto y ordena crear 2 pods adicionales.

### Sobre comandos kubectl:

#### ¿Qué información específica muestra cada comando y para qué sirve?

**`kubectl get nodes`**
- **Muestra**: Lista de todos los nodos del cluster
- **Información**: Nombre, estado (Ready/NotReady), roles, edad, versión
- **Uso**: Verificar que todos los servidores estén funcionando correctamente

**`kubectl get pods`**
- **Muestra**: Lista de pods en el namespace actual
- **Información**: Nombre, estado (Running/Pending/Error), reintentos, edad
- **Uso**: Monitorear el estado de las aplicaciones

**`kubectl get ns`** (namespaces)
- **Muestra**: Todos los namespaces del cluster
- **Información**: Nombre, estado, edad
- **Uso**: Ver la organización lógica del cluster

**`kubectl -n kube-system get pods`**
- **Muestra**: Pods del sistema Kubernetes
- **Información**: Componentes internos como etcd, api-server, scheduler
- **Uso**: Diagnosticar problemas de infraestructura

**`kubectl get pods -o wide`**
- **Muestra**: Información extendida de los pods
- **Información adicional**: IP del pod, nodo donde está ejecutándose
- **Uso**: Debugging y análisis de red

**`kubectl delete pod <nombre>`**
- **Acción**: Elimina un pod específico
- **Efecto**: Si es parte de un deployment, se crea uno nuevo automáticamente
- **Uso**: Reiniciar pods problemáticos

**`kubectl apply -f archivo.yml`**
- **Acción**: Aplica configuración desde archivo YAML
- **Efecto**: Crea o actualiza recursos definidos en el archivo
- **Uso**: Despliegue de aplicaciones y configuraciones

### Sobre la arquitectura:

#### ¿Cómo se comunican los diferentes componentes entre sí?

**Comunicación via API Server**:
- **Todos los componentes** se comunican únicamente a través del API Server
- **API Server** es el único que accede directamente a etcd
- **kubectl** envía comandos al API Server mediante HTTPS
- **Kubelet** reporta estado al API Server regularmente

**Flujo de comunicación típico**:
1. **kubectl** envía comando al **API Server**
2. **API Server** valida y guarda en **etcd**
3. **Scheduler** lee de API Server y decide dónde colocar pods
4. **Kubelet** del nodo objetivo recibe instrucciones del API Server
5. **Kubelet** reporta estado de vuelta al API Server

#### ¿Qué sucede cuando el nodo master falla?

**Escenarios de falla del Master**:

**Falla temporal (minutos)**:
- Los nodos trabajadores siguen funcionando normalmente
- Las aplicaciones continúan sirviendo tráfico
- **No se pueden hacer cambios** (crear/eliminar pods, deployments, etc.)
- kubectl no funciona

**Falla prolongada (horas)**:
- Si un nodo worker falla, **no se pueden crear pods de reemplazo**
- **No hay rebalanceo automático**
- Las aplicaciones existentes siguen corriendo pero sin gestión

**Solución: Alta disponibilidad del Master**:
- **Múltiples nodos master** (3 o 5 típicamente)
- **etcd distribuido** en múltiples servidores
- **Load balancer** para el API Server
- **Failover automático** entre masters

## Resumen Expandido de Conceptos Clave

### 1. **Kubernetes (K8s)**
- **Definición**: Orquestador de contenedores que automatiza despliegue, escalado y gestión
- **Beneficio principal**: Elimina el trabajo manual de gestionar contenedores
- **Analogía**: Como un director de orquesta que coordina todos los músicos (contenedores)

### 2. **Pods**
- **Definición**: Unidad mínima de despliegue, contiene uno o más contenedores
- **Característica clave**: Contenedores en el mismo pod comparten IP y almacenamiento
- **Ciclo de vida**: Efímeros - se crean y destruyen según necesidad

### 3. **Deployments**
- **Definición**: Plantilla que define cómo deben verse los pods
- **Ventaja**: Gestión declarativa - "dices qué quieres, no cómo hacerlo"
- **Funciones**: Rolling updates, rollbacks, escalado automático

### 4. **Réplicas**
- **Concepto**: Múltiples copias idénticas del mismo pod
- **Objetivo**: Alta disponibilidad y distribución de carga
- **Comportamiento**: Si una réplica falla, Kubernetes crea otra automáticamente

### 5. **Nodo Master (Control Plane)**
- **Función**: Cerebro del cluster que toma todas las decisiones
- **Componentes críticos**: API Server, etcd, Scheduler, Control Manager
- **Responsabilidad**: Mantener el estado deseado del cluster

### 6. **kubectl**
- **Definición**: CLI (línea de comandos) para interactuar con Kubernetes
- **Poder**: Permite gestionar todo el cluster desde comandos simples
- **Comunicación**: Habla con el API Server usando REST APIs

### 7. **Conceptos Avanzados**

#### **Escalabilidad Horizontal vs Vertical**
- **Horizontal**: Agregar más pods (réplicas)
- **Vertical**: Dar más recursos (CPU/RAM) a pods existentes
- **K8s favorece**: Escalabilidad horizontal por defecto

#### **Tolerancia a Fallos**
- **Self-healing**: Se repara automáticamente
- **Health checks**: Verifica continuamente que todo funcione
- **Graceful degradation**: Si algo falla, el resto sigue funcionando

#### **Inmutabilidad**
- **Pods son inmutables**: No se modifican, se reemplazan
- **Actualizaciones**: Se crean pods nuevos y se eliminan los viejos
- **Beneficio**: Consistencia y predictibilidad

### 8. **Flujo de Trabajo Típico**
```
Developer → kubectl → API Server → etcd → Scheduler → Kubelet → Container Runtime
```

### 9. **Estados de Recursos**
- **Desired State** (Estado deseado): Lo que quieres que pase
- **Current State** (Estado actual): Lo que está pasando realmente
- **Reconciliation** (Reconciliación): Proceso de hacer que coincidan

### 10. **Namespace (Espacios de Nombres)**
- **Propósito**: Organizar recursos lógicamente
- **Analogía**: Como carpetas en un sistema de archivos
- **Uso común**: Separar desarrollo, testing y producción
