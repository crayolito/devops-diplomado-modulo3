## Pods, Deployments y Recursos Avanzados

## Creación de Pods

### Conceptos Básicos

- **Pod**: Unidad básica donde se pueden crear uno o varios contenedores
- **Comando de verificación**: `kubectl get nodes` para obtener información de los nodos

### Comandos Fundamentales

#### Verificación de Namespaces

```bash
kubectl get ns
```

**¿Qué hace este comando?**

- Muestra todos los **namespaces** (espacios de nombres) del cluster
- Los namespaces son formas lógicas de organizar y agrupar nuestros pods
- Permiten separar recursos por proyecto, ambiente (dev/test/prod), o equipos

#### Información de Pods

**¿Cuál es el comando para ver información de mi pod?**

```bash
kubectl get pods
kubectl get pods -o wide  # Para más detalles
kubectl describe pod <nombre-pod>  # Información completa
```

#### Aplicar Configuraciones

```bash
kubectl apply -f <archivo.yml>
```

**¿Qué hace este comando?**

- **Aplica** configuraciones definidas en archivos YAML
- **Crea** recursos nuevos si no existen
- **Actualiza** recursos existentes si ya existen
- Es **declarativo**: describes el estado deseado, no los pasos

## Configuración de Pods con Múltiples Contenedores

### Pregunta Clave: ¿Cómo ejecutar 2 contenedores (nginx y mongo) en un pod?

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-mongo-pod
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
    - name: mongo
      image: mongo:latest
      ports:
        - containerPort: 27017
      env:
        - name: MONGO_INITDB_ROOT_USERNAME
          value: "admin"
        - name: MONGO_INITDB_ROOT_PASSWORD
          value: "password123"
```

## Deployments - Plantillas Avanzadas

### Estructura Básica

```yaml
apiVersion: apps/v1 # Versión de API para aplicaciones
kind: Deployment
metadata:
  name: mi-aplicacion
spec:
  replicas: 5
  selector:
    matchLabels:
      app: mi-aplicacion
  template:
    metadata:
      labels:
        app: mi-aplicacion
    spec:
      containers:
        - name: contenedor-principal
          image: mi-imagen:latest
```

### Comportamiento de Réplicas

#### ¿Qué hacen las réplicas?

- **replicas: 5** → Crea 5 pods idénticos
- **Alta disponibilidad**: Si un pod falla, los otros 4 siguen funcionando
- **Distribución de carga**: El tráfico se distribuye entre los 5 pods

#### ¿Qué pasa si cambio de 5 a 3 réplicas y aplico?

```bash
# Cambiar replicas: 5 → replicas: 3 en el YAML
kubectl apply -f deployment.yml
```

**Resultado**: Kubernetes **eliminará 2 pods automáticamente** para llegar al estado deseado (3 réplicas)

## Tipos de Deployments

### 1. Deployment (Estándar)

- **Comportamiento**: Aleatorio, coloca pods donde hay recursos disponibles
- **Uso**: Aplicaciones sin estado (stateless)

### 2. DaemonSet

- **Comportamiento**: Coloca **exactamente un pod en cada nodo**
- **Cantidad de pods = Cantidad de nodos en el cluster**
- **Uso**: Monitoreo, logs, agentes de seguridad
- **Ejemplo**: Si tienes 4 nodos, se crearán 4 pods (uno por nodo)

### 3. StatefulSet

- **Comportamiento**: Similar a Deployment pero con **volúmenes persistentes**
- **Uso**: Bases de datos, aplicaciones que necesitan almacenamiento persistente
- **Característica**: Cada pod tiene su propio volumen asociado

## Anatomía Completa de un Pod

### Estructura YAML Detallada

```yaml
apiVersion: v1 # Primera línea: versión de Kubernetes
kind: Pod # Tipo de recurso
metadata:
  name: mi-pod-completo # Nombre del pod
  labels:
    app: mi-aplicacion
    version: "1.0"
spec:
  containers:
    - name: mi-contenedor
      image: mi-imagen:latest
      env: # Variables de entorno
        - name: DATABASE_URL
          value: "mongodb://localhost:27017"
        - name: NODE_IP
          valueFrom:
            fieldRef:
              fieldPath: status.hostIP # Referencia a propiedades de Kubernetes
      resources: # Gestión de recursos
        requests: # Recursos mínimos garantizados
          memory: "150Mi"
          cpu: "100m"
        limits: # Límites máximos
          memory: "200Mi"
          cpu: "200m"
      readinessProbe: # ¿Está listo para recibir tráfico?
        httpGet:
          path: /health
          port: 8080
        initialDelaySeconds: 30
        periodSeconds: 10
      livenessProbe: # ¿Está funcionando correctamente?
        tcpSocket:
          port: 8080
        initialDelaySeconds: 60
        periodSeconds: 20
      ports:
        - containerPort: 8080
```

## Gestión de Recursos

### Analogía con Internet

- **Requests**: Como un plan de internet mínimo (150 Mbps garantizados)
- **Limits**: Como el máximo de tu plan (200 Mbps máximo)
- **Kubernetes garantiza**: Los recursos mínimos solicitados
- **Evita**: Que una aplicación consuma todos los recursos del nodo

### Ejemplo Práctico

```yaml
resources:
  requests:
    memory: "512Mi" # Kubernetes reserva mínimo 512MB
    cpu: "250m" # Kubernetes reserva mínimo 0.25 CPU cores
  limits:
    memory: "1Gi" # Máximo 1GB de RAM
    cpu: "500m" # Máximo 0.5 CPU cores
```

## Health Checks (Sondas de Salud)

### ReadinessProbe - "¿Estás listo?"

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 30 # Espera 30 segundos antes de la primera verificación
  periodSeconds: 10 # Verifica cada 10 segundos
```

**Propósito**:

- Evita enviar tráfico a pods que aún no están listos
- Especialmente útil para aplicaciones Java que tardan en inicializar

### LivenessProbe - "¿Estás vivo?"

```yaml
livenessProbe:
  tcpSocket:
    port: 8080
  initialDelaySeconds: 60
  periodSeconds: 20
```

**Propósito**:

- Detecta si el contenedor se "colgó" o dejó de funcionar
- Si falla, Kubernetes reinicia el contenedor automáticamente

### Diferencia Clave

- **LivenessProbe**: "¿El contenedor está funcionando?"
- **ReadinessProbe**: "¿El contenedor puede procesar peticiones?"

## Estado de Pods

### Comando de Verificación

```bash
kubectl get pods
```

### Interpretación de READY

```
NAME        READY   STATUS    RESTARTS
mi-pod      0/1     Pending   0        # No está listo
mi-pod      1/1     Running   0        # Listo y funcionando
mi-pod      2/2     Running   0        # 2 contenedores, ambos listos
```

**¿Qué significa READY?**

- **0/1**: 0 contenedores listos de 1 total → **No está listo**
- **1/1**: 1 contenedor listo de 1 total → **Completamente operativo**
- **2/2**: 2 contenedores listos de 2 total → **Todos funcionando**

## Actualización de Recursos

### ¿Qué pasa si quiero agregar más recursos a un pod existente?

**Problema**: Los pods son **inmutables** - no se pueden modificar una vez creados

**Solución**:

1. **Modificar el Deployment** YAML con los nuevos recursos
2. **Aplicar** con `kubectl apply -f deployment.yml`
3. **Kubernetes crea pods nuevos** con los recursos actualizados
4. **Elimina los pods viejos** gradualmente (rolling update)

**¿Esto detendrá todo?**

- **No**, gracias al **rolling update**
- Los pods viejos siguen funcionando hasta que los nuevos estén listos
- **Zero downtime deployment**

## StatefulSet vs Deployment

### ¿Qué es StatefulSet?

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: database-cluster
spec:
  replicas: 3
  serviceName: database
  selector:
    matchLabels:
      app: database
  template:
    metadata:
      labels:
        app: database
    spec:
      containers:
        - name: postgres
          image: postgres:13
          env:
            - name: POSTGRES_PASSWORD
              value: "secretpassword"
  volumeClaimTemplates: # ¡Esta es la diferencia clave!
    - metadata:
        name: postgres-storage
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 5Gi
```

### Diferencias Clave

| Característica        | Deployment             | StatefulSet              |
| --------------------- | ---------------------- | ------------------------ |
| **Identidad**         | Pods intercambiables   | Pods con identidad única |
| **Almacenamiento**    | Sin estado (stateless) | Con estado (stateful)    |
| **Volúmenes**         | Compartidos o ninguno  | Volumen dedicado por pod |
| **Orden de creación** | Paralelo               | Secuencial (0, 1, 2...)  |
| **Casos de uso**      | APIs, frontend         | Bases de datos, caches   |

### Ejemplo con Proveedores Cloud

```yaml
# En AWS/Azure, cada pod de StatefulSet obtiene:
# - Volumen EBS/Azure Disk de 5GB
# - Respaldo automático
# - Persistencia incluso si el pod se elimina
```

## Resumen de los 3 Tipos de Deployment

### 1. **Deployment** (Estándar)

- **Propósito**: Aplicaciones sin estado
- **Comportamiento**: Coloca pods donde hay recursos disponibles
- **Garantiza**: Número de réplicas solicitadas
- **Uso típico**: APIs REST, frontends, microservicios

### 2. **DaemonSet**

- **Propósito**: Un pod por nodo
- **Comportamiento**: Deployment en cada nodo del cluster
- **Garantiza**: Exactamente un pod por nodo
- **Uso típico**: Monitoring (Prometheus), logs (Fluentd), seguridad

### 3. **StatefulSet**

- **Propósito**: Aplicaciones con estado
- **Comportamiento**: Crea réplicas con volúmenes asociados
- **Garantiza**: Persistencia de datos y identidad única
- **Uso típico**: Bases de datos (MongoDB, PostgreSQL), caches (Redis)

## Exposición de Pods - Introducción a Services

### El Problema

- Los pods están **encapsulados** dentro del cluster
- Los usuarios **no pueden acceder** directamente desde internet
- Necesitamos **exponer** estos contenedores hacia afuera

### La Solución: Services

- **Services.yml**: Archivo de configuración para exponer pods
- **Próximo tema**: Cómo configurar services para hacer accesibles las aplicaciones
- **Frontend**: Necesita ser accesible desde navegadores externos

## Consideraciones de Performance

### Importancia de las Pruebas

- **Pruebas de estrés**: ¿Cuánta CPU/memoria necesita mi aplicación?
- **Pruebas de concurrencia**: ¿Cuántos usuarios simultáneos puede manejar?
- **Generación de reportes**: Aplicaciones pesadas necesitan más recursos

### Análisis de Recursos por Nodo

```
Memoria total del nodo: 8GB
Pods planificados: 4 pods
Memoria por pod: ~2GB máximo
CPU total: 4 cores
CPU por pod: ~1 core máximo
```

**Planificación importante**: Analizar cuánto consumen los servidores según los pods que vamos a crear

## Comandos de Referencia Rápida

```bash
# Gestión básica
kubectl get pods                    # Ver todos los pods
kubectl get pods -o wide           # Ver pods con más detalles
kubectl describe pod <nombre>      # Información completa del pod
kubectl get ns                     # Ver namespaces
kubectl get nodes                  # Ver nodos del cluster

# Aplicar configuraciones
kubectl apply -f pod.yml           # Crear/actualizar desde archivo
kubectl apply -f deployment.yml    # Crear/actualizar deployment
kubectl delete pod <nombre>        # Eliminar pod específico

# Debugging
kubectl logs <nombre-pod>          # Ver logs del pod
kubectl exec -it <nombre-pod> sh   # Acceder al contenedor
kubectl get events                 # Ver eventos del cluster
```
